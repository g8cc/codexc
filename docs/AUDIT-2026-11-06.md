## 继续优化：长队列与状态查询

原队列解析为每个 checkbox 构造 lines[i+1:]，即使下一行就是下一项也复制所有剩余行；dispatch、enqueue 和 leaves 三处同类扫描已改为索引遍历，保留任务合同、围栏和错误语义。

|---|---:|---:|
| 10,000 | 0.9608 | 0.0728 |
| 20,000 | 3.1880 | 0.1560 |

原始对比：`/private/tmp/ck-queue-optimization-benchmark.json`，源码基线：`/private/tmp/ck-opt-baseline-uxh881in`。4 万项回归约束 5 秒轮询预算，避免把微秒级性能数字写成脆弱测试。

ck status 直接 read_text 导致 FIFO 注册表/status/PID/journal 卡死，且无限读取 journal 和超大状态。旧版五种 FIFO 输入逐一超过 5 秒，超大状态仍显示执行中。现在非阻塞打开、验证普通文件类型，状态/注册表最多读取 1 MiB、PID 最多 32 字节，journal 只读取最后 1 MiB 并去除截断的首行。七项 status-audit 覆盖这些问题、长日志尾部最新记录、大队列、多项目可见性和 benchmark 入口。

状态基准原脚本缺少 CK_COMMON_DIR，旧版启动即 unbound variable；现按被测脚本所在目录指定 helper。100 个小项目、3 次采样，状态查询中位数 0.3581 → 0.3706 秒，未测得加速（约 3.5% 波动/开销）；不得把长队列收益泛化到小项目状态查询。基准确认 fixture 未改写：`/private/tmp/ck-status-optimization-benchmark.json`。

邻接场景测量：4 万项 leaves 审计 0.363 秒，enqueue 新任务 1.159 秒，均核对数量/退出码。性能修复随全工具复审的最终完整入口验证通过，日志：`/private/tmp/ck-tests-p8bok78p`；之前运行 `/private/tmp/ck-tests-_2_si_w1` 的失败情况见上节。

## 工程燃料与持续加料

新增 `ck-prompts.py`，内置 correctness、reliability、security、edge-cases、test-coverage、performance、observability、dependencies、maintainability、documentation 十类指令。每类限定真实缺口、复现、小步修复和验证，避免仅为消耗配额制造任务。

`ck prompts list/show/add` 管理内置及 `.codingkeeper/prompts/*.md` 项目指令；新增文件完整写入后原子发布，拒绝覆盖已有项目指令。`burn-cursor.json` 保存轮换位置。新 Prompt 可在运行期间加入，默认每两遍完整燃料库没有源文件变化后进入非活跃 waiting_fuel，保持在线且不发送模型请求。新 ready 任务、或项目 Prompt 新增/修改会自动恢复；队列任务始终优先。人工 loop.halt 不会被加料清除。

`ck enqueue` 接受文字、`--file` 或 `--prompt`，与验收共享锁，多行验收合同逐字保留；不把文本当 shell 执行，不丢并发添加任务，未完成验收事务会明确阻止改写队列。headless evidence 保存 worker Prompt、输出和 burn 目标；审查收到具体燃料目标。CLI 与桌面识别 waiting_fuel，不把等待算成模型执行。

`zcodec run` 默认全天与 burn 开启。显式 `CODEXC_LOOP_IDLE=0` 等待队列；显式时间窗仍约束 headless worker/gate/review 和 watchdog。自定义 CODEXC_LOOP_IDLE 文本或 CODEXC_PROMPT_ROTATION=0 保留原单指令及空转停炉语义。

## 追加审计：ZCode 空会话

用户反馈后继续检查真实 ZCode 0.17 CLI 包与会话数据库，发现 worker 将 OpenCode 的 `ses_` 校验误用于 ZCode。真实帮助文本明确写 `--resume <sessionId> ... (sess_...)`，会话创建函数为 `sess_${crypto.randomUUID()}`，当前库有 692 个 `sess_` ID。旧 worker 既不续接已保存的真实 ID，也会拒绝真实成功输出里的 ID，造成上下文持续丢失。旧假 CLI 回归全部使用 `ses_`，因此未发现该错误。

另一个独立根因是首次失败/空回答时丢弃已创建的会话 ID，超时更会绕过成功输出解析。现在使用已安装版本支持的 `--output-format stream-json`，在 `turn.started` 出现时原子保存 `.codingkeeper/zcode-session-id.retry`，无需等模型完成；下一轮明确 `--resume`，成功且有效回答后再提升为主会话。已有主会话优先且失败不覆盖；拒绝损坏本地 ID 及恢复后的 ID 突变。子工具事件不会替换根会话。新回归先在旧 worker 上复现 8 处断言失败，包含真实格式 ID、连续失败、空回答、损坏保存文件；另加入 SIGKILL、无效最终 metadata 与首次配额通知场景。

只读归因：fingerprint / sale / soul2soul 共 175 个零 token 且带自动工作任务标记的失败会话。按更严格条件（完整 `[codexc-headless]` 用户输入前缀、根会话、error outcome、无 assistant 文本/推理/工具操作、无模型消耗、无子会话和任务链接、未被当前 worker 选中）筛出 173 个：fingerprint 67、sale 60、soul2soul 46。清理前再次逐条核对时间戳和内容，再执行 ZCode `sessionStore.softDeleteSession` 相同的 `time_deleted` 更新。消息、parts、用量和附件均保留，当前会话与其他来源的历史记录未清理。

当前 watchdog 巡逻不调用旧 `cli_alive()` 的模型探测函数，因此本轮未将历史健康探测误认为当前新增来源。ZCode 独立审查有意创建独立上下文；失败的独立审查与用户手动建立的会话不在此次自动工作会话清理范围。没有发起真实模型请求。CLI 在 `turn.started` 前崩溃且没有任何 ID 输出时无法保存续接信息，此边界不能由外层适配器凭空恢复。
