# 排障手册（triage playbook）— 从三次误判事件沉淀

> 2026-11-07 定稿。案例：用户三次报告界面有会话残留，排障者 grep 八层存储三次宣布
> "干净"，三次全错。真实标题是 "Reply OK"（带空格），检索键却是用户的转写词
> "replyOK"。本文是该事件的完整复盘与可执行规则，适用于一切 UI 层报障的排障。

## 案例时间线（哪一轮错在哪）

| 轮次 | 动作 | 结果 | 错误根因 |
|---|---|---|---|
| 1 | grep `~/.dsh` 找 `replyOK` → 0 命中 | 宣布"UI 陈旧" | 模式无空格变体 + 会话文件是 zstd 压缩，双重漏检 |
| 2 | grep `~/.zcode`、tasks-index → 0 命中 | 宣布"数据干净" | 同一模式错到别的存储层 |
| 3 | 浏览器存储 UTF-16 感知搜索 → 0 命中 | 继续宣布干净 | 补了编码维度，仍没补"空格变体"维度 |
| 4 | 开浏览器亲眼看 UI，搜索 `reply` | **找到 20+ 条 "Reply OK"** | — |
| 5 | 逐会话内容校验删除 + 新实例端到端验证 | 归零 | — |

三轮"零命中"全部是**检索方式的失败**，不是目标不存在。

## 五条铁律

### 1. 先看后搜

UI 层报障的第一动作是**打开用户看的界面**（DOM 快照/截图），抄下原样字符串，再开始
任何存储检索。用户的转写词不是字面量——"replyOK" 到界面上可能是 "Reply OK"、
"Reply-OK"、大小写混合或本地化文案。拿到原样字符串前，任何 grep 都是在搜一个假设。

### 2. 宽松检索 + 变体矩阵

字符串检索先跑宽松前缀（`reply*`）而非精确词。精确命中前，变体矩阵逐维过：

| 维度 | 例子 |
|---|---|
| 空白变体 | `Reply OK` / `ReplyOK` / `Reply-OK` / `Reply_OK` |
| 大小写 | `replyOK` / `ReplyOK` / `REPLYOK` / `Reply Ok` |
| 字符编码 | UTF-16LE（浏览器 leveldb 是定长编码，普通 grep **必漏**） |
| 压缩 | zstd / gzip（会话日志、聊天记录常压缩存放，先解压再搜） |
| 渲染形变 | 截断（列表标题截断）、HTML 实体、emoji/零宽字符插入 |

### 3. 零命中 + 用户坚持 = 假定自己漏了

零命中只证明"**这个检索方式错了**"，不证明目标不存在。用户看到的东西必有数据来源。
正确反应是换维度（变体/编码/压缩/别的存储/直接观察 UI），**禁止**用同一模式重复确认
"干净"并据此反驳用户。确认偏差是排障中最贵的错误：每一轮"零命中"都在加固上一轮的
错误结论。

### 4. 验证回到用户视图

修复后必须回到**用户看到的同一界面**确认一遍（同一 URL、同一列表、同一搜索框）。
数据层自查（"文件删了"、"索引清了"）对"用户还看不看得到"没有证明力——派生缓存
（dsh 的投影缓存、ZCode 的侧栏 tasks-index）可能在渲染旧快照。

### 5. 实体删除要同步派生物

删任何实体时，核对其全部派生存储并逐层清点：

- 会话 → 索引行 / 消息 / 投影缓存 / 任务壳（如 ZCode tasks-index 的 task_id=会话 id）
- 注册表条目（如 ~/.codingkeeper/projects）
- 分组成员关系（如 dsh workspace.json 的 sessionIds）

案例教训：删了会话目录没删投影缓存 → 鬼影照旧；删了 CLI 会话行没删侧栏任务壳 →
重启后还在。

## 快速核对清单（下次排障时过一遍）

- [ ] 我打开用户看的界面了吗？原样字符串抄下来了吗？
- [ ] 检索键跑的是宽松前缀还是精确词？
- [ ] 空白/大小写/编码/压缩四个变体维度过了一遍吗？
- [ ] 有没有把"零命中"当成"用户看错了"？
- [ ] 修复后回到用户视图验证了吗？
- [ ] 实体删除后，派生存储逐层清点了吗？
