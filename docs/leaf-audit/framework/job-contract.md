# 可验证工单合同

一张工单处理一个完整用户结果，可关联一个或多个目录ID。先做有限只读核查，五项准入通过才进入ready；不得把95项原文直接当工单。

## 具体工单必填信息

```text
问题ID：项目内稳定ID
关联目录ID：一个或多个；自定义ID也可
项目与起点：真实路径、源码SHA或可识别快照、已有WIP及本轮范围
用户结果：谁在什么触发下受损，修好后如何不同
适用证据：真实功能/数据/消费者与出处
当前差距：复现步骤、预期/实际、日志/测试/测量位置
去重证据：相关源码、已有测试/提交/任务；为何尚未覆盖
价值与优先级：影响范围/严重性/频率、恢复能力、成本
范围与依赖：必要改动路径、前置环境、外部动作及已有授权
假设：当前证据支持的根因；待排除的关键不确定性
验收：复现命令或步骤、正向对照、失败判据、必需平台/层级
性能预算（适用时）：来源、设备/网络/store/数据规模/并发/样本/缓存口径
完成证据：目标SHA或diff、实际命令/结果、产物位置、未验证边界
```

未知字段不能用默认值伪装已知。可以从仓库推断的记录出处，不因缺profile而停止所有工作。只有当前证据明确支持时，才记录no-gap、covered或not-applicable；无法取得必要证据时保留candidate，或在存在明确前置阻塞时记blocked，并写清待查事项/解除条件。若缺的证据确实影响一个具体重要决定，可建范围、成本和停止条件明确的验证任务，验收是取得风险判断，不能预设已有缺陷或自动无限增加埋点/bench。

## 实施与范围

1. 对照起点和WIP确定可归属范围。允许隔离checkout/临时目录验证；不覆盖已有修改。
2. 复现相关失败/风险；正确性证据可以是异常/状态/错误结果，性能则需要可比数字。
3. 实施必要的完整改动。一个修复可能跨实现、调用方、测试和文档；超过建议文件数时复核是否仍属同一结果，记录理由，不机械回滚。
4. 运行相关验收和必要回归。基线已存在的失败与新回归分列；环境缺失保持未验证，不得计成功。引入平台专属改动就验证该平台，不能用服务端全绿代替移动SDK编译。浏览器/设备/读屏/IME行为须在所需边界验证，源码字符串、普通fill和旧产物不能替代。
5. 校验修复具有判别力：应能说明旧行为如何使验收失败；高风险或容易假绿的守卫做安全隔离的错误注入。低影响可逆改动不为形式强造测试。
6. 需要撤销时只撤本轮可归属补丁，保留证据和未解决问题。禁止重置整个工作树/文件吞掉用户修改。
7. 按现有授权和项目规则完成提交等动作。绿灯是验证结果，不能扩大授权；已获授权则无需再问一遍。

API/数据契约可以为修复而合理演进，但必须在任务范围内说明消费者、兼容策略和必要验证；禁止暗改契约凑绿。测试/预算的真实错误可以纠正，但应先明确更正前后的含义，不以更低阈值或不同负载掩盖回归。

## 结果与证据

- implemented：实现已完成但至少一项必需验证/审查欠缺；不可写成done。
- verified：已满足该工单所有必需验收，证据绑定实际SHA/diff；不代表整项目所有维度通过。
- no-change：当前目标已满足或没有支持改动的证据，附范围/理由；不强制空commit或新增守卫。
- blocked：当前缺明确前置；记录解除条件、下一动作和所有已有失败，不把问题从队列删除。
- deferred/archived：明确记录原因、决定依据、关联替代工单和复查触发条件；不是测试通过。

回复说明用户结果、实际改动、验收证据、仍有限制与下一动作。宿主要求的终止行遵循其协议，但TASK_RESULT/DONE等文字不能替代上述证据；review非零、输出缺失或必需检查SKIP不能被解析成verified。
