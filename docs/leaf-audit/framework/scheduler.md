# 有证据的工单调度

输入是项目目标、当前状态与已有问题，不是“从95条第一条开始”。本文件描述接入合同，未提供runner实现。

## 从目录到ready

1. 收集已有用户问题、真实失败、测量/发布风险；读取适用项目约定和工作树。
2. 根据实际能力选择相关ID。UI包括Web、原生、桌面；对端包括同仓SDK/客户端、契约fixture和远端服务。目录名/空peers不能单独判不适用。
3. 有限只读核查五项准入：适用、当前差距、去重、价值、验收。没有当前差距就不自动造“持续改进”；具体重要风险缺证据时，可派有范围、成本和停止条件的验证任务，产出风险判断。必要证据拿不到不等于no-gap，保留candidate或明确前置的blocked。
4. 将同一根因和用户结果合并为稳定项目问题ID，关联多个目录标签。已有实现未验收进入implemented/review-needed，不再次投喂实现。
5. 用PRIORITY的实际损害排序已准入工单；能力目录和ID顺序不参与调度。最大优先级/时间窗口/资源预算只是执行边界，不代表范围外问题不存在。

## 状态与保留

建议保留：problem_id、catalog_ids、source/evidence、severity、status、base/head或diff摘要、required_checks、attempts、last_failure、blocked_reason、next_action、复查触发条件。

| 状态 | 含义 | 允许的下一步 |
|---|---|---|
| candidate | 尚未满足准入 | 有限只读核查、合并、归档理由 |
| ready | 有具体差距与有效验收且前置满足 | 领取并记录基线 |
| in-progress | 正在处理，同问题避免重复领取 | 实施/验证/记录失败 |
| implemented / review-needed | 已有改动，缺必需验证或审查 | 绑定精确diff补验；不重做 |
| verified | 该合同验收完整 | 带证据归档；新回归仍可重新打开 |
| blocked | 缺具体前置，问题仍未解决 | 写解除条件/下一动作，解除后恢复原问题 |
| deferred | 已明确延后且有理由 | 保留严重性和复查时间/触发 |
| archived | covered/no-gap/not-applicable/duplicate/明确放弃等 | 保留原因、替代ID和适用范围 |

旧系统如仅支持ready/review-needed/done，应由adapter显式映射并保存旁路元数据；未实现字段不得假装已被机器执行。done仅映射verified或有证据的无改动结论，不能映射“失败次数到限”。

## 失败与重试

失败是信息，不是失去优先级的理由。同根因连续失败时暂停相同策略，保留问题、日志、失败SHA、假设与已排除方向；做根因复核/选择不同验证方法/寻求必要输入。不得两次失败就写skip_leaves，也不得降低严重性。

重要问题blocked时，调度器可以在不影响它的前提下处理独立、有价值且前置满足的任务；必须继续显示原问题与解除动作，不自动宣称这一档已经完成。没有可执行有价值任务则停机/等待，不生成补量或源码扫描任务填满额度。

## 验收接入要求

- worker和review使用本任务精确base/head或归属diff；recent-3提交不能替代。
- 分别记录进程退出状态、输出解析状态、所需检查执行状态和审查结论；无输出/非法结果/非零退出保持失败，不能被清理命令exit0盖掉。
- 验收检查限定合同平台与证据口径。SKIP/无设备/旧产物不得计PASS；测试总数不能代替关键路径。
- reviewer默认按审查授权工作；若只读审查遇到需写构建产物的验证，使用受授权的隔离目录，不偷偷改业务或队列。
- 不自动commit/push/deploy、不清理用户WIP；遵循现有授权。并行任务避免同问题/同文件冲突。
