# 本框架的工程约定

本目录是候选检查方法库，不授权更改任何目标项目、部署、发消息或消费模型额度。用户当前与此前已给出的授权和适用仓库约定决定动作范围；不要重复请求已获授权的常规操作。

## 先决定问题是否值得做

读取[README.md](README.md)、[job-contract.md](job-contract.md)、相关[taxonomy.md](taxonomy.md)条目。每个ready工单都需要：

1. 实际存在且受影响的功能/消费者/资源。
2. 当前SHA或可识别快照上的可复现差距；具体重要风险缺证据时，只能先派有范围、成本和停止条件的验证任务，不能预设修复。纯缺测试、缺某库不够。
3. 已查源码、测试、Git、队列，未被等价实现或其他工单覆盖。
4. 清楚的用户/运维/安全/维护收益与合理成本。
5. 能判别成功和失败的验收，已明确所需环境和权限。

行为失败、异常、错误响应、不可达控件也是有效基线，不强制所有任务都有数字。性能必须有可比工作负载、预算来源和前后数据。参考阈值不自动构成缺陷。

## 实施纪律

- 记录起点SHA或可识别快照、工作树差异与已有WIP；工作树不干净不自动阻塞。能够分离则独立实施/验证，不能分离的冲突才需协调。
- 一张工单对应一个完整结果；必要时同时改实现、调用方、测试、文档。文件数只提示范围复核，不是回滚理由；不得夹带无关重构。
- 不为测试绿而删除/skip/弱化断言、降低预算、隐藏错误或改变工作负载。旧测试本身错误或预算失真时，先写清证据与更正合同，再改并保留历史对照。
- 不使用git reset/checkout/restore整文件来清理失败实验；只撤能证明属于本轮的补丁，保护用户和其他agent修改。保留可诊断失败的证据；不必丢弃有价值的未完成实现。
- 编译/测试只按真实产品与改动范围选必要检查。已有gate已执行的检查不再嵌套成一层“测试测试”。SKIP、缺工具/设备、审查器无结果均不是PASS。
- 提交取决于既有授权和项目规范，验证绿不自动授权commit/push/deploy。获得授权后继续完成，不为框架创造额外审批。

## 目录维护

95个ID保持可追溯；它们是标签，不是排序。多个ID可归同一问题，项目自定义ID允许保留。修改条目时同步检查taxonomy、PRIORITY和prompts的适用解释，不制造重复待办。

本框架合同与taxonomy是当前方法约定。prompts中的历史数字、固定错误码、自动commit/回滚和“只改一处”等文字只是旧线索，不能直接成为当前工单；派单者应删除冲突片段并带入已评审的项目合同。
